# Design Standard Checklist Generator

## 1. 目的

各種設計標準書から、レビューで実際に使用できるチェックリストを作成する。

処理の基本フロー:

設計標準書
→ 文書構造解析
→ 規定候補抽出
→ 規定ID付与
→ 要求事項化
→ Atomic Check分解
→ チェックID付与
→ 重要度付与
→ トレーサビリティ付与
→ Coverage確認
→ チェックリスト出力

単なる要約ではなく、標準書の規定を「確認可能な質問」に変換する。

## 2. 対象文書

- 画面設計標準
- 画面設計書記述標準
- 基本設計標準
- 詳細設計標準
- 詳細記述書設計標準
- 帳票設計標準
- API設計標準
- DB設計標準
- バッチ設計標準
- IF設計標準
- コーディング標準
- セキュリティ設計標準
- テスト設計標準
- プロジェクト固有標準

入力形式:
- PDF
- Word
- Excel
- Markdown
- Text

## 3. 必須原則

1. 標準書に記載されていない規定を標準由来として追加しない。
2. チェック項目には可能な限り出典を付与する。
3. 曖昧な規定を勝手に断定しない。
4. 1チェック項目=1確認事項を基本とする。
5. 条件付き規定は条件を保持する。
6. 例外規定を欠落させない。
7. 必須・禁止・推奨・任意を混同しない。
8. AI推奨事項を追加する場合は、標準由来と明確に分離する。
9. ページ番号、章節、出典を推測で作らない。
10. Yes / No / N/A で判定可能な粒度を目指す。

## 4. 処理手順

### STEP 1: 入力文書の識別

次を取得する。

- 文書名
- 文書種別
- バージョン
- 制定日
- 改訂日
- 対象工程
- 対象成果物

不明な項目は「不明」とする。

### STEP 2: 文書構造解析

次を抽出する。

- 章
- 節
- 項
- 見出し
- 本文
- 表
- 注記
- 補足
- 例外規定
- 禁止事項

### STEP 3: 規定候補抽出

以下の表現を重点的に抽出する。

- ～すること
- ～とする
- ～であること
- ～を記載する
- ～を設定する
- ～を使用する
- ～してはならない
- ～は禁止する
- ～を必須とする
- ～を推奨する
- 原則～
- 必須
- 禁止
- 推奨
- 任意
- 原則として

### STEP 4: 規定ID付与

例:

- STD-UI-001
- STD-UI-002
- STD-DD-001
- STD-DB-001
- STD-API-001

推奨プレフィックス:

- UI: 画面
- RD: 帳票
- BD: 基本設計
- DD: 詳細設計
- DB: データベース
- API: API
- IF: 外部IF
- BAT: バッチ
- SEC: セキュリティ
- CODE: コーディング
- TEST: テスト

### STEP 5: 規定分類

規範レベル:

- Mandatory
- Prohibited
- Conditional Mandatory
- Recommended
- Optional
- Reference

品質観点:

- 完全性
- 正確性
- 一貫性
- 命名
- UI
- 入力
- 出力
- エラー処理
- 例外処理
- ログ
- DB
- API
- IF
- バッチ
- トランザクション
- 排他
- セキュリティ
- 性能
- 保守性
- アクセシビリティ
- トレーサビリティ

### STEP 6: 要求事項化

標準書:
「画面項目には項目IDを付与すること」

要求:
「すべての画面項目に項目IDが定義されている」

チェック:
「すべての画面項目に項目IDが付与されているか？」

### STEP 7: Atomic Check分解

複数確認事項を含む規定は必ず分割する。

悪い例:
「項目ID、項目名、型、桁数、必須区分が正しく記載されているか？」

良い例:
- 項目IDが記載されているか？
- 項目名が記載されているか？
- データ型が記載されているか？
- 桁数が記載されているか？
- 必須/任意区分が記載されているか？

### STEP 8: チェックID付与

例:

- CHK-UI-001
- CHK-DD-001
- CHK-DB-001

1規定から複数チェックを生成してよい。

### STEP 9: 属性付与

各チェック項目には以下を持たせる。

- No
- Check ID
- Category
- Sub Category
- Check Point
- Severity
- Requirement
- Source Document
- Chapter
- Section
- Page
- Standard ID
- Condition
- Exception
- Result
- Evidence
- Reviewer
- Review Date
- Comment

### STEP 10: 重要度設定

Critical:
- 法令
- 情報漏洩
- 認証/認可
- 重大障害
- データ破壊

High:
- 必須規定
- 機能障害
- 不整合
- 主要な例外処理欠落

Medium:
- 品質
- 保守性
- 統一性
- 可読性

Low:
- 推奨
- 軽微な表記
- 参考的な改善

標準書に定義がある場合は標準書を優先する。

### STEP 11: 重複整理

判定:

- 完全重複
- 類似
- 親子関係
- 条件違い

完全重複は統合可能。
複数標準を根拠とする場合は、出典を複数保持する。

### STEP 12: トレーサビリティ検証

最低限、以下を追跡可能にする。

Check ID
→ Standard ID
→ Source Document
→ Chapter
→ Section
→ Page

### STEP 13: Coverage検証

Coverage =
チェック項目化済み対象規定数
/
チェック対象規定総数
× 100

必須・禁止規定は100%を目標とする。

別途以下を出力する。

- 未変換規定
- 要確認規定
- 曖昧規定
- 出典欠落規定

### STEP 14: 最終出力

以下を生成する。

1. 標準書一覧
2. 規定抽出一覧
3. レビューチェックリスト
4. 標準→チェック項目トレーサビリティ表
5. 未変換規定一覧
6. Coverageレポート
7. AI推奨事項（要求された場合のみ）

## 7. 出力ルール

推奨Markdown:

| No | Check ID | 分類 | チェック項目 | 重要度 | Standard ID | 根拠 | 結果 | コメント |
|---:|---|---|---|---|---|---|---|---|

判定値:

- OK
- NG
- N/A
- Pending

## 8. 品質自己チェック

出力前に以下を確認する。

- 必須規定の抽出漏れがない
- 禁止規定の抽出漏れがない
- 条件付き規定の条件が残っている
- 例外条件が残っている
- 1項目に複数観点を詰め込んでいない
- 出典を追跡できる
- AI推測が標準由来に混ざっていない
- 完全重複項目がない
- 未変換規定が明示されている
- Coverageが算出されている

## 9. 禁止事項

- 標準書にない規定の捏造
- 出典の捏造
- ページ番号の推測
- 必須と推奨の混同
- 条件の削除
- 例外の削除
- 根拠不明項目の標準由来扱い
- 複数観点の過度な1行集約

## 10. ユーザー向け実行例

ユーザー:
「添付した画面設計標準からチェックリストを作成してください」

実行:
1. 標準書を読み込む
2. 文書構造を解析する
3. 規定を抽出する
4. 規定IDを付ける
5. Atomic Checkへ変換する
6. チェックIDを付ける
7. 根拠を付ける
8. 重複を除く
9. Coverageを確認する
10. チェックリストを出力する

ユーザー:
「画面設計標準と詳細設計標準を横断してレビュー表を作って」

実行:
1. 標準書別に規定を抽出
2. 規定IDを文書種別ごとに付与
3. 横断的に重複を分析
4. 統合チェックリストを生成
5. 各チェック項目に複数出典を紐付ける
6. 標準書別Coverageも算出する
