# Design Standard Checklist Generator

## 1. 目的

各種設計標準書から、レビューで実際に使用できるチェックリストを作成する。

```
設計標準書
 → 文書構造解析 → 規定候補抽出 → 規定ID付与 → 要求事項化 → Atomic Check分解
 → チェックID付与 → 重要度付与 → 重複整理 → トレーサビリティ → Coverage確認
 → チェックリスト出力
```

単なる要約ではなく、標準書の規定を「確認可能な質問」に変換する。

この Skill の判断はすべて**原文の文字列に対して**行う。標準書に書かれていない語を
出力に持ち込まないことが、成果物が信用される唯一の根拠になる。判断に迷ったら
「原文のどこを根拠にそう言えるか」を先に確認する。示せないなら、その判断はしない。

参照ファイル:

| ファイル | 読むタイミング |
|---|---|
| [`references/classification.md`](references/classification.md) | STEP 3/5/10。規範レベル・品質観点・重要度の語彙表と判定順序 |
| [`references/conversion-rules.md`](references/conversion-rules.md) | STEP 6/7。要求事項化と Atomic Check 分解の具体例、分解してはいけない形 |
| [`references/table-standards.md`](references/table-standards.md) | 標準書が表形式のとき |
| [`references/output-formats.md`](references/output-formats.md) | STEP 14。成果物の列定義と出力ルール |
| [`templates/`](templates) | 出力時。CSV/Markdown の列構成をそのまま使う |

## 2. 対象文書

- 画面設計標準 / 画面設計書記述標準
- 基本設計標準
- 詳細設計標準 / 詳細記述書設計標準
- 帳票設計標準
- API設計標準
- DB設計標準
- バッチ設計標準
- IF設計標準
- コーディング標準
- セキュリティ設計標準
- テスト設計標準
- プロジェクト固有標準

入力形式: PDF / Word / Excel / Markdown / Text

形式によって取れる情報が違う。Word は見出しレベルを持つので章・節を正確に追える。
Excel は表の列（区分・重要度・分類）が使える。PDF はページ番号が取れる。
Markdown / Text はページ番号を持たない。**取れない情報は「不明」とし、推測で埋めない**（必須原則 9）。

## 3. 必須原則

1. 標準書に記載されていない規定を標準由来として追加しない。
2. チェック項目には可能な限り出典を付与する。
3. 曖昧な規定を勝手に断定しない。
4. 1チェック項目 = 1確認事項を基本とする。
5. 条件付き規定は条件を保持する。
6. 例外規定を欠落させない。
7. 必須・禁止・推奨・任意を混同しない。
8. AI推奨事項を追加する場合は、標準由来と明確に分離する。
9. ページ番号、章節、出典を推測で作らない。
10. Yes / No / N/A で判定可能な粒度を目指す。

原則 1 と 3 は同じことの裏表になっている。標準書が「適切な名称」としか書いていないのに
命名規則を補って書くと、レビュアーは標準書に無い基準で指摘することになる。
書かれていないことは、書かれていないと出力する。

## 4. 処理手順

### STEP 1: 入力文書の識別

次を取得する。取れないものは「不明」とする。

- 文書名 / 文書種別 / バージョン / 制定日 / 改訂日 / 対象工程 / 対象成果物

文書種別は ID プレフィックスを決めるので、最初に確定させる。
利用者の指定があればそれに従う。指定が無いときだけ、文書名と冒頭の本文から推定する。

| 種別 | プレフィックス | 推定に使う語 |
|---|---|---|
| 画面設計標準 | `UI` | 画面, UI |
| 帳票設計標準 | `RD` | 帳票, レポート |
| 基本設計標準 | `BD` | 基本設計 |
| 詳細設計標準 | `DD` | 詳細設計, 詳細記述 |
| DB設計標準 | `DB` | DB, データベース, テーブル |
| API設計標準 | `API` | API |
| IF設計標準 | `IF` | IF設計, 外部IF, インタフェース |
| バッチ設計標準 | `BAT` | バッチ, batch |
| セキュリティ設計標準 | `SEC` | セキュリティ |
| コーディング標準 | `CODE` | コーディング, コード規約 |
| テスト設計標準 | `TEST` | テスト |
| その他標準 | `GEN` | （上記に当たらない場合） |

推定語は上から順に当てる。「画面」と「テスト」の両方を含む文書名なら画面設計標準になる。

複数の標準書を扱うときは、文書ごとに `DOC-001` 形式の標準書IDも振る。
一度使った番号は、その標準書を取り下げても再利用しない。既に配った成果物が
指すIDを別の標準書が名乗ると、トレーサビリティが崩れるため。

### STEP 2: 文書構造解析

本文を「章 / 節 / 見出し / 本文 / 表 / 注記」に切り分け、各行に所在を割り当てる。

章・節は**本文中に実在する表記からのみ**採る。

- `第3章 画面設計` → 章 = 3
- `3.2 項目定義` → 節 = 3.2、章 = 3（節番号の先頭から取れる）
- `3 画面設計` → 章 = 3
- `(1) …` `1) …` → 箇条書き。見出しではない

章見出しが現れたら節はいったん未設定へ戻す。文書は上から順に読まれる前提で、
直前に現れた見出しを後続の行が引き継ぐ。

見出し行そのものは規定候補から外す。見出しは規定ではないので、
「3.2 項目定義」を「項目定義しているか？」に変換してはいけない。

表形式の標準書は行自身が章・節の列を持っていることがある。その場合は見出しの
追跡結果より列の値を優先する。見出しの追跡は推測を含むが、列の値は標準書の記載そのものであるため。
→ [`references/table-standards.md`](references/table-standards.md)

### STEP 3: 規定候補抽出

行を文（`。` 区切り）に分け、行頭の箇条書き記号（`-` `・` `(1)` など）を落とす。
6文字未満の断片は規定として扱わない。

**「ただし」「但し」「なお、」「例外として」で始まる文は、直前の規定の例外として引き継ぐ。**
独立した規定として立てると、本体の規定から例外が切り離されて欠落する（必須原則 6）。

```
「主キーを定義すること。ただし、履歴テーブルはこの限りではない。」
  → 規定1件（本体）、その Exception = 「ただし、履歴テーブルはこの限りではない」
  → 規定2件にはしない
```

規範表現をひとつも含まない文は規定候補ではない。抽出対象の語彙は
[`references/classification.md`](references/classification.md) にまとめてある。

### STEP 4: 規定ID付与

`STD-<プレフィックス>-<連番3桁>`。文書内の出現順に振る。

```
STD-UI-001, STD-UI-002, STD-DD-001, STD-DB-001, STD-API-001
```

### STEP 5: 規定分類

#### 規範レベル

`Mandatory` / `Prohibited` / `Conditional Mandatory` / `Recommended` / `Optional` / `Reference`

**判定は順序が重要**。上から順に当て、最初に成立したものを採る。

1. **禁止表現があれば `Prohibited`**。標準書が表の「区分」列に何と書いていても、
   本文が「してはならない」なら禁止。禁止の取りこぼしは影響が大きい（必須原則 7）。
2. 表に**区分列**があればその値。標準書自身の分類なので推定より優先する。
3. **任意表現があり、明示的な必須表現が無ければ `Optional`**。
   「任意とする」の「とする」を必須語尾と取ると、任意規定が必須に化ける。
4. **必須表現 + 条件表現 → `Conditional Mandatory`**（必須原則 5）。
5. **必須表現 + 推奨表現 → `Recommended`**。「原則として～すること」は推奨側。
6. **必須表現のみ → `Mandatory`**。
7. **推奨表現のみ → `Recommended`**。
8. 本文に規範表現が無くても、表の**重要度列**に値があれば `Mandatory` として拾う。
   標準書がその行に重要度を与えているのは、レビューで確認する対象として挙げている
   ということ。ただし強さは書かれていないので、根拠は「重要度列:高」の形で残す。
9. どれにも当たらなければ規定候補ではない。捨てる。

判定に使った語は必ず控えておく。「この文をなぜ必須と判定したか」を後から示せないと、
レビュー時に規定かどうかの議論が再燃する。

#### 品質観点（分類）

完全性 / 正確性 / 一貫性 / 命名 / UI / 入力 / 出力 / エラー処理 / 例外処理 / ログ /
DB / API / IF / バッチ / トランザクション / 排他 / セキュリティ / 性能 / 保守性 /
アクセシビリティ / トレーサビリティ

決める順序:

1. 表の**分類列**（標準書自身の分類）
2. **規定文そのもの**
3. **見出し**

見出しを最後にするのは、文書名や大見出しが全行に効いてしまい、細かい分類を潰すため。
「画面設計標準」という見出しの下にあるセキュリティ規定は、セキュリティに分類したい。

どれでも決まらなければ `完全性` に置く。捨てるよりは人の目に触れさせる。

### STEP 6: 要求事項化

規定文（～すること）を、状態の記述（～している）へ変換する。**語尾の変換だけを行う**。

```
標準書  : 画面項目には項目IDを付与すること
要求    : 画面項目には項目IDを付与している
チェック: 画面項目には項目IDを付与しているか？
```

語を足したり言い換えたりしない。「項目IDを付与すること」を
「一意な項目IDを漏れなく付与している」にすると、「一意」も「漏れなく」も標準書には無い。

変換表と、禁止規定・体言止めの扱いは [`references/conversion-rules.md`](references/conversion-rules.md) を見る。

### STEP 7: Atomic Check 分解

1チェック = 1確認事項（必須原則 4）。分解する形は2つある。

**並列動作**（`～し、` `～を行い、` `～とし、` で繋がる）:

```
必須項目は識別可能な表示を行い、未入力の場合はエラー表示すること
 → 必須項目は識別可能な表示を行っているか？
 → 必須項目は未入力の場合にエラー表示する設計になっているか？
```

先頭節の主題（`必須項目は`）を後続節へ引き継ぐ。引き継がないと2つ目が
「未入力の場合はエラー表示しているか？」になり、単体では何の話か分からない。
引き継ぐ主題は**原文の文字列をそのまま複製する**（語彙を足さない）。

**列挙**（`A、B、Cを記載すること`）:

```
画面項目には項目ID、項目名、データ型、桁数を記載すること
 → 画面項目には項目IDを記載しているか？
 → 画面項目には項目名を記載しているか？
 → 画面項目にはデータ型を記載しているか？
 → 画面項目には桁数を記載しているか？
```

前置き（`画面項目には`）は全項目で共有する。

**分解してはいけない形がある。** 分けると意味が変わるものを機械的に切ると、
標準書に無い規定を作ることになる（必須原則 1）。判断基準は
[`references/conversion-rules.md`](references/conversion-rules.md) の 6・7 節にまとめてある。
特に `または` `もしくは` `いずれか` `かつ` `等` `など` を含む文は分けない。

条件の付き方は分解の種類で違う。

- **並列動作**: 条件はそれを含む節にだけ効く。他の節へ広げない。
- **列挙**: 前置きの条件は全項目に共通するので引き継ぐ。

**例外規定は独立したチェックとして必ず残す**（必須原則 6）。

```
例外規定「ただし、履歴テーブルはこの限りではない」の適用有無が設計上明確になっているか？
```

分解した結果が短すぎて（8文字未満）判定できない場合、および曖昧表現しか含まない
参考規定は、チェック化せず**未変換規定**として理由付きで残す。

- `確認可能な粒度に変換できない (規定文が短く述部を特定できない)`
- `曖昧表現のみで構成され、判定基準が標準書内に定義されていない`

黙って落とすと Coverage が実態より良く見える。落としたことを見えるようにする。

### STEP 8: チェックID付与

`CHK-<プレフィックス>-<連番3桁>`。1規定から複数チェックを生成してよい。

採番は STEP 11 の重複統合を済ませてから行う。統合で消える項目に番号を配ると、
出力される番号が飛ぶ。

### STEP 9: 属性付与

各チェック項目が持つ列（[`templates/checklist-template.csv`](templates/checklist-template.csv) と同じ）:

`No` / `Check ID` / `Category` / `Sub Category` / `Check Point` / `Severity` /
`Requirement` / `Standard ID` / `Source Document` / `Chapter` / `Section` / `Page` /
`Condition` / `Exception` / `Result` / `Evidence` / `Reviewer` / `Review Date` / `Comment`

`Sub Category` は規定が属する見出しの末尾を使う。例外チェックは `例外` とする。

### STEP 10: 重要度設定

**標準書に重要度の記載があれば、それが最優先**。推定は書かれていないときの代替手段にすぎない。

書かれていない場合、上から順に当てる。判定対象は「規定文 + 分類名」。
分類名も見るのは、分類「セキュリティ」のように観点が分類側にしか現れないことがあるため。

1. `Critical` 観点語（法令 / 情報漏洩 / 認証 / 認可 / 暗号 / データ破壊 / SQLインジェクション …）に当たれば **Critical**
2. `Prohibited` → **High**。違反時の影響が大きいので、観点語が無くても High 以上に置く
3. `Mandatory` / `Conditional Mandatory` → **High**
4. `Recommended` → 品質観点語（保守 / 統一 / 可読 / 命名 …）に当たれば **Medium**、無ければ **Low**
5. `Optional` → **Low**
6. `Reference`（規範レベルを判定できなかった規定）→ **Medium**。落とさず中位に置いて人の目に触れさせる

判定根拠（どのキーワードに当たったか）を控えておく。「なぜ Critical なのか」を
説明できないと、重要度は運用で無視されるようになる。

語彙は [`references/classification.md`](references/classification.md)。

### STEP 11: 重複整理

チェック項目の文言を比較用に正規化してから突き合わせる。
全角/半角・空白・句読点・括弧の違いだけで別物と判定されるのを防ぐため、
NFKC 正規化し、空白と `。、・「」()` 等を落とす。**語そのものは変えない。**

- **完全重複**（正規化後に一致）: 統合する。統合された側の出典も**両方保持する**。
- **類似**（0.88 以上）: 統合せず「候補」として報告するに留める。
- **親子関係 / 条件違い**: 統合しない。条件が違うものを1つにすると条件が落ちる。

自動で統合するのは完全重複だけにする。似ているという理由で削ると、
微妙に違う規定が消え、その規定は誰にもレビューされなくなる。

**同一規定を Atomic 分解した兄弟同士は重複候補にしない。** 定義上、別の確認事項として
意図的に分けたものなので、候補に並べても確認の手間が増えるだけになる。

### STEP 12: トレーサビリティ検証

最低限これを追跡可能にする。

```
Check ID → Standard ID → Source Document → Chapter → Section → Page
```

統合された項目は出典を複数持つ。1つに丸めない。
出典が取れなかった箇所は空欄ではなく「不明」を入れる。空欄だと
「まだ埋めていない」のか「取得できない」のか区別が付かない。

### STEP 13: Coverage 検証

```
Coverage = チェック項目化済み対象規定数 / チェック対象規定総数 × 100
```

分母は `Mandatory` / `Prohibited` / `Conditional Mandatory` / `Recommended` に限る。
参考記述まで含めると率が薄まり、必須規定の取りこぼしが見えなくなる。

`Mandatory` / `Prohibited` / `Conditional Mandatory` は **100% を目標**とする。

対象が0件のときは 100% とする。「対象となる規定が1件も無い」のは未達ではない。
0% にすると、禁止規定を含まない標準書が常に警告を出してしまう。

併せて次を報告する。

- 未変換規定（理由付き）
- 曖昧表現を含む規定
- 出典（章・節・ページ）を特定できない規定
- 類似チェック項目の候補

指摘が1件も無いときも、確認済みであることが分かるよう1行残す。
空欄のレポートは「まだ実行していない」ように見える。

### STEP 14: 最終出力

1. 標準書一覧
2. 規定抽出一覧
3. レビューチェックリスト
4. 標準→チェック項目トレーサビリティ表
5. 未変換規定一覧
6. Coverage レポート
7. AI推奨事項（**要求された場合のみ**）

列構成は [`templates/`](templates)、出力の細部は
[`references/output-formats.md`](references/output-formats.md) に従う。

AI推奨事項は 1〜6 とは別ファイルにし、全行に「AI推奨（標準書由来ではない）」を入れる。
`Standard ID` / `Chapter` / `Section` / `Page` の列は**持たせない**。持たせると
出典があるように見え、標準由来の項目と取り違えられる（必須原則 8）。
提案するのは「標準書に規定が無い観点」だけにする。標準書に書いてあることを
言い換えて出しても、標準由来の項目と重複するだけで価値が無い。

## 5. 画面設計標準の重点観点

標準書に存在する場合、以下を確認する。

画面ID / 画面名称 / レイアウト / 項目ID / 項目名称 / データ型 / 桁数 / 必須・任意 /
初期値 / 活性・非活性 / 表示・非表示 / 入力制御 / 入力チェック / ボタン / イベント /
画面遷移 / メッセージ / エラー表示 / 権限制御 / アクセシビリティ

## 6. 詳細設計標準の重点観点

標準書に存在する場合、以下を確認する。

処理概要 / 入力 / 出力 / 前提条件 / 事後条件 / 処理フロー / 分岐条件 / DBアクセス /
SQL / トランザクション / 排他制御 / エラー処理 / 例外処理 / ログ / 外部IF / API /
バッチ / リトライ / タイムアウト / セキュリティ / 性能

5章・6章の観点は**チェック項目の材料ではない**。標準書がこれらに触れていない場合に
「標準書に規定が無い観点」として AI推奨事項へ回すためのもの（必須原則 8）。
標準書にある規定は STEP 3 で原文から拾う。

## 7. 出力ルール

Markdown のチェックリストは最低限この形にする。

```markdown
| No | Check ID | 分類 | チェック項目 | 重要度 | Standard ID | 根拠 | 結果 | コメント |
|---:|---|---|---|---|---|---|---|---|
```

判定値: `OK` / `NG` / `N/A` / `Pending`（初期値は `Pending`）

CSV は Excel で開けるよう UTF-8 BOM + CRLF で出力する。
出典が取得できなかった箇所は「不明」を入れる。

## 8. 品質自己チェック

出力前に確認する。

- 必須規定の抽出漏れがない
- 禁止規定の抽出漏れがない
- 条件付き規定の条件が残っている
- 例外条件が残っている
- 1項目に複数観点を詰め込んでいない
- チェック項目の語がすべて原文に由来する（言い換え・補足を足していない）
- 出典を追跡できる
- AI推測が標準由来に混ざっていない
- 完全重複項目がない
- 未変換規定が理由付きで明示されている
- Coverage が算出されている

特に見落としやすいのは「言い換え」と「例外の欠落」。
生成したチェック項目を数件抜き取り、原文と並べて、**原文に無い語が入っていないか**を確かめる。

## 9. 禁止事項

- 標準書にない規定の捏造
- 出典の捏造
- ページ番号の推測
- 必須と推奨の混同
- 条件の削除
- 例外の削除
- 根拠不明項目の標準由来扱い
- 複数観点の過度な1行集約
- 「または」「いずれか」を含む選択規定の分解

## 10. ユーザー向け実行例

### 実行例1: 単一標準書

ユーザー:「添付した画面設計標準からチェックリストを作成してください」

1. 標準書を読み込み、文書種別と版を確定する（STEP 1）
2. 章・節を割り当てる（STEP 2）
3. 規定を抽出し、規範レベルと分類を付ける（STEP 3-5）
4. 規定IDを付ける（STEP 4）
5. 要求事項化し、Atomic Check へ分解する（STEP 6-7）
6. 重複を整理してからチェックIDを付ける（STEP 11 → STEP 8）
7. 属性と重要度を付ける（STEP 9-10）
8. 出典を検証する（STEP 12）
9. Coverage を算出する（STEP 13）
10. 成果物を出力する（STEP 14）

### 実行例2: 複数標準書の横断

ユーザー:「画面設計標準と詳細設計標準を横断してレビュー表を作って」

1. 標準書別に規定を抽出する
2. 規定IDは文書種別ごとに付与する（`STD-UI-xxx` / `STD-DD-xxx` のまま変えない）
3. 文書をまたいだ完全重複を統合し、類似は候補として報告する
4. 統合チェックリストを生成する
5. 各チェック項目に**複数の出典**を紐付ける
6. 標準書別の Coverage も算出する

**チェックIDは各文書のものを維持する。** 統合表だけの新しいID体系を作ると、
文書別チェックリストとの対応が1段増えて追跡しにくくなる。

統合行の重要度は、統合した項目の中で**最も重いもの**を採る。軽い方に引きずられると、
片方の標準書が Critical としていた規定が Medium で運用されてしまう。
