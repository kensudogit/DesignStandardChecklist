# Conversion Rules

STEP 6（要求事項化）と STEP 7（Atomic Check 分解）の具体例。

通底する制約はひとつ。**変換は語尾の付け替えだけで行い、語を足さない。**
「項目IDを付与すること」を「一意な項目IDを漏れなく付与している」にすると、
「一意」も「漏れなく」も標準書には無い。レビュアーは標準書に無い基準で指摘し、
被レビュー側は標準書を見ても根拠を確認できない（必須原則 1/3）。

## 1. 規定からチェック項目への変換

### 例1

規定:
「画面項目には項目IDを付与すること」

変換:
「すべての画面項目に項目IDが付与されているか？」

### 例2

規定:
「必須項目は識別可能な表示を行い、未入力の場合はエラー表示すること」

Atomic Check:
1. 必須項目が画面上で識別可能になっているか？
2. 必須項目が未入力の場合にエラー表示する設計になっているか？

2つ目に「必須項目が」を補っているのは、原文の先頭節にある主題をそのまま複製した
もの。分解すると主語が後続節から消えるため、**原文にある文字列に限って**引き継ぐ。

## 2. 禁止規定

規定:
「パスワードをログへ出力してはならない」

チェック:
「パスワードがログへ出力されない設計になっているか？」

禁止規定は「〜していないこと」を確認する形にする。「パスワードをログへ出力して
いるか？」にすると、OK が違反を意味することになり、レビュー表として読めなくなる。

語尾の付け替えは次の表に従う。長い語尾から順に判定する。

| 原文の語尾 | 要求事項 |
|---|---|
| としてはならない / としてはいけない | としないこととしている |
| してはならない / してはいけない | しない設計になっている |
| べきではない / べきでない | ことがない設計になっている |
| てはならない / てはいけない | ない設計になっている |
| しないこと | しない設計になっている |
| は避けること / を避けること | を避けた設計になっている |
| は認めない / は許容しない | を行わない設計になっている |
| は禁止 / を禁止 / 禁止する / 禁止とする | を行わない設計になっている |

どれにも当たらない場合は「〜という禁止規定に適合している」に落とす。
無理に活用させると壊れた日本語になり、レビュー表の信用を落とす。

## 3. 条件付き規定

規定:
「外部API呼出しを行う場合はタイムアウト値を定義すること」

チェック:
「外部API呼出しを行う場合、タイムアウト値が定義されているか？」

条件を削除して、
「タイムアウト値が定義されているか？」
だけにしない。

条件を落とすと、条件に当てはまらない設計まで NG と判定されてしまう。
逆に条件を残しておけば、当てはまらない場合は `N/A` で通せる。

**条件の効く範囲は分解の種類で変わる。**

- **並列動作の分解**: 条件はそれを含む節にだけ効く。他の節へ広げない。

  ```
  ログは日次で出力し、障害発生時は即時に通知すること
   → ログは日次で出力しているか？            （条件なし）
   → ログは障害発生時に即時に通知しているか？（条件: 障害発生時）
  ```

- **列挙の分解**: 前置きの条件は全項目に共通するので、全項目へ引き継ぐ。

  ```
  外部API呼出しを行う場合はタイムアウト値、リトライ回数を定義すること
   → 外部API呼出しを行う場合、タイムアウト値を定義しているか？
   → 外部API呼出しを行う場合、リトライ回数を定義しているか？
  ```

## 4. 推奨規定

規定:
「検索結果は100件以内とすることを推奨する」

分類:
Recommended

重要度:
原則 Low または Medium

標準書で重要度指定がある場合はそれを優先する。

推奨規定を「〜すること」に書き換えて必須に見せない。推奨のまま出し、
レビューで `N/A` を選べる余地を残す（必須原則 7）。

## 5. 曖昧表現

規定:
「適切な名称を設定すること」

勝手に命名規則を作らない。

チェック:
「標準書で定義された命名規則に従った名称になっているか？」

ただし命名規則が標準書内で定義されていない場合:
「確認要: 『適切な名称』の判定基準が標準書内で明確化されていない」
とする。

曖昧表現を含んでいても、他に確認可能な要素があればチェック化してよい。

```
テーブル名は適切な接頭辞を付け、40文字以内とすること
 → 40文字以内は確認できるのでチェック化する
 → 「適切な接頭辞」については Ambiguity に残す
```

曖昧表現しか含まない参考規定だけを未変換にする。→ [10節](#10-変換できない規定)

## 6. 分解する形

分解するのは次の2つ。

### 並列動作

`～し、` `～を行い、` `～とし、` `～したうえで、` `～した上で、` で繋がる形。

```
画面項目には項目IDを付与し、項目定義書と対応付けること
 → 画面項目には項目IDを付与しているか？
 → 画面項目には項目定義書と対応付けているか？
```

先頭節の主題（`〜は` で終わる部分）を後続節へ複製する。
複製するのは原文の文字列そのもので、言い換えない。

### 列挙

`A、B、Cを記載すること` のように、**文末が列挙の述部**で終わる形。

区切りとして使えるもの:

```
、 , ・ ／ / および 及び と
```

`と` は「AもBも必要」なので分けてよい。ただし「として」「ごとに」の一部でもあるため、
前後の字を確認する。**`または` `もしくは` は選択なので分けてはいけない**（7節）。

文末の述部として認めるもの:

```
（を|が）＋ 記載 / 記述 / 定義 / 設定 / 付与 / 明記 / 指定 / 管理 /
出力 / 表示 / 添付 / 使用 / 見積も / 定め / 含め
```

前置き（`画面設計書には` `機能ごとに` `外部API呼出しを行う場合は`）は切り出して
全項目で共有する。前置きの目印になる助詞: `には` `では` `について` `ごとに` `場合は` `ときは` `は`

## 7. 分解してはいけない形

分けると意味が変わるものを機械的に切ると、標準書に無い規定を作ることになる。
次のいずれかに当たったら分解せず、1件のチェックとして残す。

### 選択・例示を含む

```
または / もしくは / いずれか / かつ / 等 / など
```

```
悪い例:
  日付は YYYY/MM/DD または YYYYMMDD の形式とすること
   → 日付は YYYY/MM/DD の形式か？   ← どちらでもよいはずが必須になった
   → 日付は YYYYMMDD の形式か？     ← 同上。両方 OK は不可能

良い例:
   → 日付は YYYY/MM/DD または YYYYMMDD の形式になっているか？
```

`かつ` は分けても論理は保たれるが、原文が明示的に1つの条件として書いている以上、
分けると「片方だけ満たす」状態を OK と判定できてしまう。

### 末尾の要素が「の」を含む

最後の名詞を全要素で共有している可能性が高い。

```
悪い例:
  桁数および範囲の入力チェックを実装すること
   → 桁数を実装しているか？          ← 意味が壊れた
   → 範囲の入力チェックを実装しているか？

良い例:
   → 桁数および範囲の入力チェックを実装しているか？
```

途中の要素に付く `の` はその要素自身の修飾なので、これには当たらない。

### 要素が助詞で終わる / 述語を含む

```
は / が / を / に / へ / で / と / も / から / まで / より
```

これらで終わる要素は列挙ではなく主題提示。`～する` `～して` `～行い` を含む要素も同様。

```
悪い例:
  テーブル定義書は、主キーを記載すること
   → 「テーブル定義書は」と「主キーを記載すること」の2件に分ける ← 列挙ではない
```

### 要素が長い（30文字超）

長い要素が並ぶ列挙は、区切りが読点なのか文の切れ目なのか判別できない。
確実でない分解はしない。

### 各要素が自前の主題を持つ

```
参照はGET、登録はPOST、更新はPUTとすること
 → 各要素が「〜は」を持っているので、前置きは切り出さない
 → 参照はGETとしているか？ / 登録はPOSTとしているか？ / 更新はPUTとしているか？
```

### 例外句

例外句は分解の対象に含めない。本文から切り離し、独立したチェックとして立てる。

```
主キーを定義すること。ただし、履歴テーブルはこの限りではない。
 → 主キーを定義しているか？                                    （Exception 欄に例外を保持）
 → 例外規定「ただし、履歴テーブルはこの限りではない」の適用有無が設計上明確になっているか？
```

## 8. 要求事項化の語尾変換表

規定文（～すること）を状態の記述（～している）にする。長い語尾から順に当てる。

| 原文の語尾 | 要求事項 |
|---|---|
| しなければならない | している |
| する必要がある | している |
| とすること | としている |
| であること | である |
| されていること | されている |
| していること | している |
| を必須とする / 必須とする | を必須としている / 必須としている |
| を推奨する / 推奨する / が望ましい | としている |
| すること | している |
| うこと | っている |
| 記載する / 記述する / 定義する / 設定する | 記載している / 記述している / 定義している / 設定している |
| 付与する / 添付する / 明記する / 管理する | 付与している / 添付している / 明記している / 管理している |
| 適用する / 作成する / 準拠する | 適用している / 作成している / 準拠している |
| とする | としている |

### 「〜ること」で終わる場合

- **え段のかな + る**（`含める` `設ける` `加える` など一段動詞）→ `〜ている`
  「含めること」→「含めている」
- **それ以外**（五段動詞）→ 活用させず `〜こととしている`
  「関連付けること」→「関連付けることとしている」

五段動詞は促音便・撥音便が語によって変わるため、機械的に活用すると壊れる。
どの動詞でも成立する形に寄せるほうが安全。

### 「〜すべきではない」（禁止）

`す` の直前がひらがなでなければサ変（名詞 + する）とみなす。

```
共有すべきではない → 共有することがない設計になっている  （「共有」= 漢字なのでサ変）
握りつぶすべきではない → 握りつぶすことがない設計になっている（五段動詞）
```

## 9. 質問文化

要求事項を Yes / No / N/A で答えられる質問にする（必須原則 10）。

| 要求事項の語尾 | 質問 |
|---|---|
| 〜か | 〜か？（そのまま） |
| 〜ない | 〜ないか？ |
| なっている | なっているか？ |
| されている | されているか？ |
| している | しているか？ |
| である | であるか？ |
| がある | があるか？ |
| ている | ているか？ |
| **サ変名詞**で終わる（体言止め） | 〜しているか？ |
| それ以外 | 〜になっているか？ |

「〜ない」を先に判定するのは、「欠落していない」が
「欠落していないになっているか？」になるのを避けるため。

サ変名詞の一覧は [`classification.md`](classification.md) 11節。
一覧に無い名詞は「〜になっているか？」に落とす。「原則」のようにサ変でない名詞を
サ変扱いすると「原則しているか？」という文が出る。

条件がある場合は質問の頭に付ける。既に質問文に条件が含まれていれば重ねない。

```
外部API呼出しを行う場合、タイムアウト値を定義しているか？
```

## 10. 変換できない規定

次の2つは無理にチェック化せず、理由を付けて未変換規定として残す。

| 理由 | 該当する規定 |
|---|---|
| `確認可能な粒度に変換できない (規定文が短く述部を特定できない)` | 分解結果が 8 文字未満で、疑問文にしても何を確認するか分からないもの |
| `曖昧表現のみで構成され、判定基準が標準書内に定義されていない` | 曖昧表現しか含まない参考規定 |

黙って落とすと Coverage が実態より良く見える。落としたことを Coverage レポートと
未変換規定一覧の両方に出す（STEP 13）。

未変換にすること自体は失敗ではない。標準書側に判定基準が無いことを可視化するのが
この欄の役目で、「未変換 0 件」を目的に無理な変換をするほうが有害。
