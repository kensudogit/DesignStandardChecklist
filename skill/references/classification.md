# Classification — 規範レベル・品質観点・重要度の語彙

STEP 3 / 5 / 10 で使う語彙表。**ここに無い語は判定に使わない。**

判定は必ず原文の文字列に対して行う（必須原則 1）。「文脈からすると必須だろう」で
規範レベルを決めると、標準書に無い強制力を付けたことになる。原文に語が無ければ
判定しない、が正しい振る舞い。

## 1. 規範レベルの判定順序

上から順に当て、最初に成立したものを採る。順序そのものが判定の一部なので、
「該当するものを全部見て一番それらしいものを選ぶ」やり方はしない。

| 順 | 条件 | 結果 | なぜこの順か |
|---:|---|---|---|
| 1 | 禁止表現を含む | `Prohibited` | 表の区分列より本文の禁止を優先する。禁止の取りこぼしは影響が大きい（必須原則 7） |
| 2 | 表に区分列がある | 区分列の値 | 標準書自身の分類。こちらの推定より確か |
| 3 | 任意表現があり、明示的必須表現が無い | `Optional` | 「任意とする」の「とする」を必須語尾と取ると任意が必須に化ける |
| 4 | 必須表現 + 条件表現 | `Conditional Mandatory` | 条件を落とさないため（必須原則 5） |
| 5 | 必須表現 + 推奨表現 | `Recommended` | 「原則として～すること」は推奨 |
| 6 | 必須表現のみ | `Mandatory` | |
| 7 | 推奨表現のみ | `Recommended` | |
| 8 | 表に重要度列がある | `Mandatory` | 標準書が重要度を与えた行はレビュー対象。強さ不明なので根拠を「重要度列:高」の形で残す |
| 9 | いずれも無い | 規定候補ではない（捨てる） | |

判定に使った語は控えておく。「なぜ必須と判定したか」を示せないと、規定かどうかの
議論がレビューのたびに蒸し返される。

### 明示的必須表現（順序 3 の判定に使う）

任意表現と競合したとき、こちらがあれば必須側に倒す。

```
遵守 / すること / とすること / であること / されていること / していること /
しなければならない / なければならない / する必要がある / が必要である /
を要する / を遵守する / 遵守すること / に従うこと / に準じる / 必須
```

## 2. 禁止表現

```
としてはならない / としてはいけない / してはならない / してはいけない /
てはならない / てはいけない / しないこと / すべきではない / べきではない /
べきでない / は避けること / を避けること / は認めない / は許容しない /
は許容されない / 許容されない / 認められない / は禁止 / を禁止 / 禁止する /
禁止とする / 不可とする / 許可しない / 使用しない / 出力しない / 設けない
```

## 3. 必須表現

```
すること / とすること / であること / していること / されていること /
を必須とする / は必須 / 必須とする / とする / を記載する / に記載する /
を設定する / を定義する / を使用する / を付与する / を行う /
しなければならない / なければならない / する必要がある / が必要である /
を要する / を遵守する / 遵守すること / に従うこと / に準じる /
記載する / 記述する / 定義する / 設定する / 付与する / 添付する /
保管する / 明記する / 管理する / 準拠する
```

文末が次で終わる場合も必須とみなす（「～を関連付けること」など）。

```
こと / ものとする / 必要がある / 必要である / とする / されたい / を要する
```

## 4. 推奨表現

```
推奨する / を推奨 / が望ましい / 望ましい / すべきである / べきである /
を原則とする / が好ましい / を基本とする / 原則として / 原則 / 可能な限り
```

`可能な限り` は推奨表現であると同時に曖昧表現でもある。両方に当たる場合、
規範レベルは `Recommended`、`Ambiguity` にも記録する。

## 5. 任意表現

```
任意とする / は任意 / してもよい / しても良い / でもよい /
選択できる / 省略できる / することができる
```

文末が次で終わる場合も任意とみなす。

```
できる / してもよい / しても良い / でもよい / で構わない
```

## 6. 条件表現

```
場合 / とき / 際は / 際に / ときは / に限り / に限って / であれば / のみ
```

条件句は**そのまま切り出す**。要約も削除もしない（必須原則 5）。
切り出す形は「`〜する場合`」「`〜のとき`」のように、条件の本体だけ。

```
外部API呼出しを行う場合はタイムアウト値を定義すること
 → Condition = 「外部API呼出しを行う場合」
```

## 7. 例外表現

```
ただし / 但し / を除き / を除く / 例外として / 例外的に /
この限りでない / この限りではない
```

文をまたいだ例外を拾うための接続表現（この語で**始まる文**は直前の規定の例外）:

```
ただし / 但し / なお、 / 例外として / 例外的に
```

## 8. 曖昧表現

```
適切な / 適切に / 適宜 / 必要に応じて / 十分な / 分かりやすい /
わかりやすい / 可能な限り / 望ましい形 / 極力 / なるべく
```

当たった場合、次の形で `Ambiguity` に残す。

```
確認要: 曖昧表現「適切な」の判定基準が標準書内で明確化されていない
```

曖昧表現を含む規定でも、他に確認可能な要素があればチェック化する。
曖昧表現しか無い参考規定だけを未変換にする。→ [`conversion-rules.md`](conversion-rules.md) 5節

## 9. 品質観点（分類）

上から順に当て、最初に一致したものを採る。順序は「具体的な観点を優先し、
一般的な観点を後ろに置く」という考え方で並んでいる。`セキュリティ` を後ろに置くと、
「認証情報を暗号化して保存すること」が `DB` に分類されてしまう。

| 分類 | 判定語 |
|---|---|
| セキュリティ | セキュリティ, 認証, 認可, 権限, 暗号, パスワード, 個人情報, 漏洩, 改ざん, CSRF, XSS, SQLインジェクション |
| トランザクション | トランザクション, コミット, ロールバック |
| 排他 | 排他, ロック, 楽観, 悲観 |
| DB | テーブル, カラム, 主キー, 外部キー, インデックス, SQL, DB, データベース, 正規化 |
| 性能 | 性能, レスポンスタイム, スループット, タイムアウト, 件数上限 |
| API | API, エンドポイント, リクエスト, レスポンス, HTTP, REST, ステータスコード |
| IF | 外部IF, インタフェース, インターフェース, 連携ファイル, 電文 |
| バッチ | バッチ, ジョブ, スケジュール, リラン, リトライ |
| エラー処理 | エラー, 異常時, 失敗時 |
| 例外処理 | 例外処理, 例外時, 例外ハンドリング, exception |
| ログ | ログ, 監査証跡, トレースログ |
| 入力 | 入力チェック, 入力制御, バリデーション, 必須項目, 未入力, 入力 |
| 出力 | 出力, 帳票, 印刷, ダウンロード |
| UI | 画面, ボタン, レイアウト, 遷移, メッセージ, 活性, 非活性, 表示 |
| アクセシビリティ | アクセシビリティ, スクリーンリーダ, コントラスト, 代替テキスト |
| 命名 | 命名, ネーミング, プレフィックス, 接頭, 物理名, 論理名, 名称規則 |
| トレーサビリティ | トレーサビリティ, 追跡, 対応表 |
| 保守性 | 保守, 共通化, 重複コード, コメント |
| 一貫性 | 統一, 一貫, 揃える |
| 正確性 | 正確, 誤り, 整合 |
| 完全性 | 網羅, 漏れ, すべて, 全て |

既定値は `完全性`。

表の分類列が上記の分類名そのものを書いている場合（「完全性」「セキュリティ」など）は、
語彙一致に頼らずその値をそのまま使う。標準書自身の分類を、語彙表に無いという理由で
捨ててしまうと、本文から別の分類が付いてしまう。

## 10. 重要度の語彙

### Critical

法令 / 情報漏洩 / 認証・認可 / 重大障害 / データ破壊。

```
法令 / 法律 / 個人情報保護 / コンプライアンス / 情報漏洩 / 漏洩 /
認証 / 認可 / 権限制御 / アクセス制御 / 暗号化 / パスワード / 機密 /
データ破壊 / データ消失 / 重大障害 / システム停止 / SQLインジェクション / XSS / CSRF
```

### High

機能障害 / 不整合 / 主要な例外処理欠落。

```
障害 / 不整合 / 整合性 / トランザクション / 排他 / ロールバック /
例外処理 / エラー処理 / タイムアウト / リトライ / 必須
```

### Medium

品質 / 保守性 / 統一性 / 可読性。

```
保守 / 統一 / 一貫 / 可読 / 命名 / コメント / 共通化
```

### 標準書に重要度が明示されている場合

これらが原文にあれば、キーワード判定より優先する。

| 重要度 | 表記 |
|---|---|
| Critical | 重要度：Critical, 重要度:Critical, 重大, 致命的 |
| High | 重要度：High, 重要度:High, 重要度：高, 重要度:高 |
| Medium | 重要度：Medium, 重要度:Medium, 重要度：中, 重要度:中 |
| Low | 重要度：Low, 重要度:Low, 重要度：低, 重要度:低, 軽微 |

## 11. 語彙を増やすとき

標準書ごとに言い回しは違うので、語彙が足りないことは普通に起きる。
足すときは次を確かめる。

1. **その語が実際に標準書の原文にあるか。** 想像で足さない。
2. **他の判定を壊さないか。** 短い語ほど誤爆する。`と` を必須表現に入れると
   「として」「ごとに」まで拾ってしまう。
3. **どの節に足すべきか。** 「原則」は推奨表現だが、体言止めの述語ではない。
   サ変名詞の一覧（下記）に入れると「原則しているか？」という文が生まれる。

### サ変名詞（体言止めを疑問文にするときに使う）

「〜する」を伴って述語になる名詞。表形式の標準書に多い体言止めの規定を
「〜しているか？」に変換するために使う。

```
一致 / 統一 / 整合 / 準拠 / 網羅 / 定義 / 記載 / 記述 / 明記 / 併記 /
明示 / 実装 / 設定 / 分離 / 分割 / 連携 / 対応 / 考慮
```

ここに無い語は「〜になっているか？」に落とす。推測で広げず、確認した語だけを並べる。
