# Examples

[`sample-standard.md`](sample-standard.md) を入力として、この Skill の手順を通した結果。
CSV は本リポジトリの実装（`backend/app/core/`）で生成したものなので、
**手順どおりに処理すれば同じ結果になる**ことを確認できる。

| ファイル | 対応するSTEP |
|---|---|
| [`sample-standard.md`](sample-standard.md) | 入力（画面設計標準の抜粋） |
| [`sample-extracted-rules.csv`](sample-extracted-rules.csv) | STEP 3-6 規定抽出一覧 |
| [`sample-checklist.csv`](sample-checklist.csv) | STEP 14 レビューチェックリスト |
| [`sample-traceability.csv`](sample-traceability.csv) | STEP 12 トレーサビリティ表 |

7つの規定から12件のチェック項目が出る。1件ずつ、何を確認するための例かを示す。

## STD-UI-001 — 列挙の分解

```
項目定義表には項目ID、項目名称、データ型、桁数を記載すること
```

→ `CHK-UI-001` 〜 `CHK-UI-004` の4件。前置き「項目定義表には」を全項目で共有し、
述部「を記載すること」も全項目に付け直している。追加した語はひとつも無い。

## STD-UI-002 — 例外の保持

```
項目の初期値を定義すること。ただし、参照専用項目の初期値は定義を省略できる。
```

「ただし」の文は独立した規定にせず、直前の規定の `Exception` へ入る。
そのうえで例外そのものを確認する `CHK-UI-006` を立てる。

規定を2件にすると「参照専用項目の初期値は定義を省略できる」が単独の任意規定として
並び、本体の必須規定と切り離される。片方だけ見た人が誤った判断をする。

## STD-UI-003 — 分解してはいけない列挙

```
日付項目は YYYY/MM/DD または YYYYMMDD の形式とすること
```

`または` を含むので分解しない。分けると「両方の形式であること」を求めることになり、
標準書が許した選択肢が消える。1件のまま `CHK-UI-007` にする。

## STD-UI-004 — 推奨規定

```
主要な操作ボタンは画面下部に配置することを推奨する
```

`Recommended` / `Low`。「配置すること」に書き換えて必須に見せない。
語尾は「を推奨する」→「としている」の置換だけで作る。

結果の `主要な操作ボタンは画面下部に配置することとしているか？` は、こなれた日本語では
ない。それでも語を足して整えないのは、整えた瞬間に「その語はどこから来たのか」を
説明できなくなるため。**読みやすさより出典の追跡可能性を優先する。**

## STD-UI-005 — 並列動作の分解と主題の引き継ぎ

```
必須項目は識別可能な表示を行い、未入力の場合はエラー表示すること
```

→ 2件。2件目に「必須項目は」を引き継いでいる（原文にある文字列をそのまま複製）。
引き継がないと「未入力の場合はエラー表示しているか？」になり、何の項目の話か分からない。

条件「未入力の場合」は2件目にだけ効く。1件目へは広げない。

`Rule Type` は `Conditional Mandatory`（必須表現 + 条件表現）。
`Category` が `エラー処理` なのは、規定文に「エラー」が含まれるため。
分類の判定順で `エラー処理` が `入力` より先に来る。

## STD-UI-006 — 禁止規定

```
パスワードを画面遷移のURLパラメータに含めてはならない
```

「〜していないこと」を確認する形にする。`Severity` は `Critical`（`パスワード` が
Critical 観点語）。「パスワードをURLパラメータに含めているか？」にすると
OK が違反を意味することになる。

`Section` が `不明` なのは、この規定が「## 5 セキュリティ」直下にあり節番号を持たないため。
推測で `5.1` を作らない。

## STD-UI-007 — 曖昧表現

```
画面設計は適切な粒度で行うこと
```

「適切な粒度」の基準は標準書内に無い。勝手に基準を作らず、チェック項目としては
原文どおりに出したうえで `Ambiguity` 列に残す。

```
確認要: 曖昧表現「適切な」の判定基準が標準書内で明確化されていない
```

Coverage レポートでは「曖昧表現を含む規定 1件」として報告される。

## Page 列が全行 `不明` である理由

入力が Markdown でページ番号を持たないため。空欄にせず `不明` を入れるのは、
「まだ埋めていない」のか「取得できない」のかを読み手が区別できるようにするため。
PDF を入力にすればここに実際のページが入る。
