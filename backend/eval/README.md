# 変換精度の評価

標準書 → チェックリストの変換 (SKILL.md STEP 3-7) が、**どれだけ正しく変換できているか**を
数値で出す仕組み。ロジックを変えたときに「変わった」ではなく「良くなった / 悪くなった」を
言えるようにするためのもの。

## 使い方

```bash
cd backend
python -m eval.runner                    # 全体のスコアを表示
python -m eval.runner --details          # 不一致を1件ずつ表示（改善作業はここから）
python -m eval.runner --gold 画面設計標準  # 対象を絞る
python -m eval.runner --json out.json    # 機械可読な結果を書き出す
python -m eval.runner --check-baseline   # baseline より悪化していたら exit 1
python -m eval.runner --update-baseline  # 現在値を baseline.json に記録する
```

`pytest` にも組み込んである (`tests/test_eval_baseline.py`)。taxonomy / extractor / atomizer を
触ってチェックリストの中身だけが静かに悪化した場合、テストの数は変わらないので通常のテストでは
気づけない。ここで止める。

**精度を上げたら `--update-baseline` を実行してコミットに含める。**

## 何を測っているか

| 指標 | 意味 |
| --- | --- |
| 規定抽出 P/R/F1 | 標準書の規定を過不足なく拾えているか。誤抽出 (P) は必須原則 1、取りこぼし (R) は必須原則 7 に対応 |
| 確認事項 P/R/F1 | Atomic Check への分解が適切か。取りこぼし = 分解不足、過剰 = 単体で判定できない項目の混入 |
| 規範レベル正解率 | 必須 / 禁止 / 条件付き必須 / 推奨 / 任意 の判定 (必須原則 7) |
| 分類正解率 | カテゴリの妥当性。チェックリストの並び順と読みやすさに効く |
| 条件の保持率 | 条件付き規定の条件を落としていないか (必須原則 5) |
| 例外の保持率 | 例外規定を落としていないか (必須原則 6) |
| 曖昧表現の正解率 | 「適切な」等を勝手に断定せず確認要にできているか (必須原則 3) |
| 変換可否の正解率 | 変換できない規定を未変換として正しく残せているか |

## 正解データ (gold) の作り方

`gold/manifest.csv` に標準書を1行足し、同じ名前で CSV を2枚置く。Excel で編集してよい
(UTF-8 BOM 付き)。

### `<名前>.rules.csv` — 抽出されるべき規定

| 列 | 書き方 |
| --- | --- |
| Rule Key | `R01` のような一意なキー。checks.csv から参照する |
| Original Rule | 標準書の原文。句点は有無どちらでもよい。**これが一致判定のキー** |
| Rule Type | `Mandatory` など。判断が割れる規定は `Recommended\|Mandatory` と `\|` 区切りで併記すればどちらも正解になる |
| Category | 同上。空にするとその規定の分類は評価しない |
| Condition | 保持されるべき条件の語。空欄は「条件が付かないのが正しい」の意味になる |
| Exception | 保持されるべき例外の語。同上 |
| Ambiguity | 曖昧表現として検出されるべきなら `yes` |
| Convertible | チェック項目に変換できるべきなら `yes`。`no` なら未変換で残るのが正解 |
| Note | 判断の根拠。**なぜその正解にしたかを必ず書く**。後から見て揉めないため |

**rules.csv は網羅であることが前提。**ここに書かれていない規定を実装が抽出したら誤抽出として
数える。逆に言えば「適用範囲」「用語定義」など規定ではない文は、書かないこと自体が正解の表明になる。

### `<名前>.checks.csv` — 作られるべき確認事項

| 列 | 書き方 |
| --- | --- |
| Check Key | `R01-1` のような一意なキー |
| Rule Key | どの規定から作られるべきか |
| Expected | 人が読むための期待文言。**判定には使わない** |
| Must Include | `;` 区切り。この語がすべて含まれていれば一致とみなす |
| Must Not Include | `;` 区切り。1つでも含まれていたら不一致 |
| Note | 判断の根拠 |

文言そのものを一致条件にしていないのは、言い回しは実装の都合で変わるため。文言で縛ると
改善のたびに正解を書き直すことになり、評価が保守されなくなる。一方 `Must Include` に主語を
入れておけば「分解したら主語が落ちた」は検出できる。この粒度を狙っている。

割当は gold 1件に対して実装の出力1件。候補が複数あるときは最も短いものを採る
(余計な語が少ないほど、その gold が意図した確認事項である可能性が高い)。

## corpus/ について

`corpus/外部設計標準.md` は**評価専用の文書**で、実在の標準書ではない。`samples/` の標準書は
デモ用に文体を揃えてあり、ルールベースの限界がスコアに現れにくい。文末表現の揺れ・実質的な
禁止・条件表現の言い換えなど、実文書に現れる書き方を意図的に集めてある。

`samples/外部IF設計標準.md` とは別物。あちらはアプリを試すためのサンプル、こちらは
限界を測るための当て馬。

ただしこれは開発用の当て馬でしかない。**本当の精度は自社の実際の標準書で測ること。**
手持ちの標準書を1本足して gold を作れば、そのままこの仕組みで測れる。

## 残っている変換の課題

現在の未達 5件はすべて同じ性質のもので、正規表現では安全に解けない。

| 課題 | 例 | なぜ難しいか |
| --- | --- | --- |
| 後続名詞の共有 | 「桁数および範囲の入力チェックを定義すること」→「桁数の入力チェック」「範囲の入力チェック」に分けたい | 「桁数および範囲」で切ると「桁数を定義する」になり意味が変わる。共有されているのが後続名詞かどうかは構文解析が要る |
| 同上 | 「正常時と異常時のHTTPステータスコード」 | 同上 |
| 述部までに語が挟まる | 「処理の開始と終了をログに出力すること」 | 「を」と動詞の間に「ログに」があり、列挙の述部として認識できない |
| 同上 | 「実行時刻および実行順序を運用設計書と対応付けて記載すること」 | 同上 |
| 見出しと本文の競合 | 「入力項目にはラベルを関連付けること」（アクセシビリティ章） | 本文の「入力」が先に当たる。見出しを優先すると別の規定で誤分類が増える |

いずれも「日本語の係り受けをどう読むか」の問題で、語彙を足しても解けない。上4件がこのあと
述べる AI補助の対象で、最後の1件（分類）は対象外。

## AI補助 (STEP 7) を有効にして測る

上の並列分解だけを Claude に手伝わせるモードがある（既定は無効、[llm_split.py](../app/core/llm_split.py)）。

```bash
python -m eval.runner --llm-candidates   # 補助に回る規定文を一覧表示 (API不要・無料)
python -m eval.runner --llm              # 補助を有効にして測る (ANTHROPIC_API_KEY が必要)
```

`--llm-candidates` は現在 8件。ルールベースが1件にしか分解できず、かつ並列の接続詞
（および / 及び / と）を含む規定だけが対象で、それ以外は Claude に投げない。

**Claude は「原文のどこで切るか」しか答えない。**返ってきた区切りは
`原文 == prefix + item1 + 接続語 + item2 + ... + suffix` を1文字単位で検証し、
合わなければ捨ててルールベースの結果を使う。原文に無い語がチェック項目に入る経路は無い。

応答は規定文をキーに `eval/llm-split-cache.json` へ保存する。同じ標準書を再解析しても
チェック項目が増減せず、Check ID がずれない（ずれると記入済みのレビュー結果が別項目に付く）。

補助が正しく判定した場合の到達点は、仕込んだ応答で確認済み：**確認事項 F1 100.0%**
（取りこぼし 0 / 過剰 0）。残るのは分類の1件だけ。ただしこれは仕組みの上限であって、
Claude が実際にどれだけ正しく判定するかは `--llm` を実行して測ること。

## 制約

- 確認事項の一致判定はキーワード一致であって意味の一致ではない。gold の `Must Include` が
  緩いと、間違った確認事項を正解と数えてしまう。語は絞って書く。
- 割当は貪欲法なので、`Must Include` が似通った gold が同一規定内に複数あると取り違え得る。
  その場合は `Must Not Include` で分ける。
- 測っているのは STEP 3-7 だけ。パース品質 (STEP 2)、重要度 (STEP 10)、重複整理 (STEP 11) は
  対象外。特にスキャン PDF の読み取り精度はここに現れない。
